# Requirements Document

## Introduction

EduNova is an AI-powered educational Android application that requires a comprehensive backend database foundation. This document specifies the requirements for establishing a scalable, normalized PostgreSQL database schema and corresponding FastAPI endpoints to support course catalogs, personalized roadmaps, learning progress tracking, and user profiles.

The backend currently supports AI chat functionality (conversations and messages) but lacks the domain data infrastructure needed for core educational features. This foundation will enable the Android frontend to display course content, track learning progress, provide personalized roadmaps, and manage user profiles.

## Glossary

- **System**: The EduNova backend API and database infrastructure
- **Database**: PostgreSQL instance hosted on Supabase
- **Android_Client**: The EduNova Android mobile application
- **User**: End user of the EduNova application
- **Course**: A structured learning path containing modules and lessons
- **Course_Module**: A logical grouping of related lessons within a course
- **Lesson**: An individual learning unit within a course module
- **Roadmap**: A curated learning path designed to achieve specific career or skill goals
- **Roadmap_Item**: An individual step or milestone within a roadmap
- **User_Progress**: Tracking data for a user's advancement through courses and lessons
- **Profile**: User account information including education mode, level, and preferences
- **Education_Mode**: Learning context (SCHOOL for K-12, GENERAL for self-directed learning)
- **API_Endpoint**: HTTP REST endpoint in the FastAPI backend
- **Migration**: Alembic database schema change script
- **Seed_Data**: Initial realistic data loaded into the database for development and testing

## Requirements

### Requirement 1: Database Schema Design

**User Story:** As a backend developer, I want a normalized, scalable database schema with proper constraints and indexes, so that the system can reliably store and query educational data.

#### Acceptance Criteria

1. THE System SHALL use UUID primary keys generated by gen_random_uuid() for all domain entities
2. WHEN a table is created, THE System SHALL include created_at and updated_at columns using TIMESTAMP WITH TIME ZONE
3. WHEN foreign key relationships exist, THE System SHALL define appropriate ON DELETE behavior (CASCADE for dependent data, RESTRICT for referenced entities)
4. THE System SHALL enforce data integrity through database-level constraints (NOT NULL, UNIQUE, CHECK, FOREIGN KEY)
5. WHEN query patterns involve foreign keys or user identifiers, THE System SHALL create indexes on those columns
6. WHERE composite uniqueness is required, THE System SHALL define composite unique constraints at the database level

### Requirement 2: User Profile Management

**User Story:** As a user, I want the system to store my profile information including education mode, level, and preferences, so that I can receive personalized learning experiences.

#### Acceptance Criteria

1. THE System SHALL store user profiles with fields: id (UUID), user_id (text, unique), full_name, email, mobile, interests, level, education_mode (enum: SCHOOL/GENERAL), created_at, updated_at
2. WHEN a profile is created, THE System SHALL enforce NOT NULL constraints on user_id, full_name, and email
3. WHEN a profile is created, THE System SHALL default education_mode to GENERAL if not specified
4. THE System SHALL support both SCHOOL mode (K-12 with class/grade) and GENERAL mode (self-directed learning)
5. WHEN the Android_Client requests GET /api/v1/profile, THE System SHALL return the authenticated user's profile data
6. WHEN the Android_Client sends PUT /api/v1/profile with profile data, THE System SHALL update the user's profile and return the updated data

### Requirement 3: Course Catalog Schema

**User Story:** As a content administrator, I want to organize courses into categories with modules and lessons, so that users can browse and enroll in structured learning paths.

#### Acceptance Criteria

1. THE System SHALL create a course_categories table with columns: id (UUID), name (unique, not null), description, display_order (integer), created_at, updated_at
2. THE System SHALL create a courses table with columns: id (UUID), category_id (FK), name, description, icon, level, duration_hours, accent_color, is_featured (boolean), created_at, updated_at
3. WHEN a course is created, THE System SHALL enforce NOT NULL constraints on category_id, name, and description
4. THE System SHALL create a course_modules table with columns: id (UUID), course_id (FK), title, description, display_order (integer), created_at, updated_at
5. THE System SHALL create a lessons table with columns: id (UUID), module_id (FK), title, description, content_type, duration_minutes, display_order (integer), created_at, updated_at
6. WHEN a course_category is deleted, THE System SHALL prevent deletion if courses reference it (RESTRICT)
7. WHEN a course is deleted, THE System SHALL cascade delete all associated modules and lessons
8. WHEN a module is deleted, THE System SHALL cascade delete all associated lessons
9. THE System SHALL create indexes on courses.category_id, course_modules.course_id, and lessons.module_id

### Requirement 4: Course Catalog API Endpoints

**User Story:** As an Android developer, I want REST endpoints to fetch courses and course details, so that the app can display course catalogs and individual course information.

#### Acceptance Criteria

1. WHEN the Android_Client requests GET /api/v1/courses, THE System SHALL return a list of all courses with basic information (id, name, description, icon, accent_color, category name)
2. WHEN the Android_Client requests GET /api/v1/courses?featured=true, THE System SHALL return only courses where is_featured is true
3. WHEN the Android_Client requests GET /api/v1/courses?category={category_id}, THE System SHALL return only courses belonging to that category
4. WHEN the Android_Client requests GET /api/v1/courses/{course_id}, THE System SHALL return complete course details including all modules and lessons
5. WHEN a requested course_id does not exist, THE System SHALL return HTTP 404 with error message
6. THE System SHALL use SQLAlchemy eager loading to avoid N+1 query problems when fetching courses with modules and lessons
7. THE System SHALL return course data matching the Android Course domain model schema (id, name, description, icon, accent)

### Requirement 5: Roadmap Schema

**User Story:** As a user, I want to browse curated roadmaps for different career paths and skill goals, so that I can follow structured learning journeys.

#### Acceptance Criteria

1. THE System SHALL create a roadmaps table with columns: id (UUID), title, category, description, level, duration, stages_count (integer), icon, accent_theme, is_system (boolean), user_id (nullable FK), created_at, updated_at
2. WHEN a roadmap is created, THE System SHALL enforce NOT NULL constraints on title, category, and level
3. THE System SHALL create a roadmap_items table with columns: id (UUID), roadmap_id (FK), title, description, skills (JSONB array), duration, display_order (integer), created_at, updated_at
4. WHEN a roadmap is deleted, THE System SHALL cascade delete all associated roadmap_items
5. THE System SHALL support both system roadmaps (is_system=true, user_id=null) and user-personalized roadmaps (is_system=false, user_id set)
6. THE System SHALL create an index on roadmaps.user_id for efficient user-specific queries
7. THE System SHALL create an index on roadmap_items.roadmap_id

### Requirement 6: Roadmap API Endpoints

**User Story:** As an Android developer, I want REST endpoints to fetch roadmaps and generate personalized roadmaps, so that the app can display learning paths to users.

#### Acceptance Criteria

1. WHEN the Android_Client requests GET /api/v1/roadmaps, THE System SHALL return all system roadmaps (is_system=true) plus authenticated user's personalized roadmaps
2. WHEN the Android_Client requests GET /api/v1/roadmaps/{roadmap_id}, THE System SHALL return complete roadmap details including all roadmap_items
3. WHEN a requested roadmap_id does not exist, THE System SHALL return HTTP 404 with error message
4. WHEN the Android_Client requests GET /api/v1/roadmaps/categories, THE System SHALL return a distinct list of all roadmap categories
5. THE System SHALL return roadmap data matching the Android RoadmapOption domain model schema (id, title, category, description, skills, level, duration, stages, icon, accentTheme)
6. THE System SHALL use SQLAlchemy eager loading to avoid N+1 query problems when fetching roadmaps with items

### Requirement 7: Learning Progress Schema

**User Story:** As a user, I want the system to track my progress through courses and lessons, so that I can see my learning advancement and resume where I left off.

#### Acceptance Criteria

1. THE System SHALL create a user_course_progress table with columns: id (UUID), user_id (text), course_id (FK), enrollment_date, last_accessed, completion_percentage (float), status (enum: NOT_STARTED/IN_PROGRESS/COMPLETED), created_at, updated_at
2. THE System SHALL enforce a unique constraint on (user_id, course_id) to prevent duplicate enrollments
3. WHEN user_course_progress is created, THE System SHALL default status to NOT_STARTED and completion_percentage to 0.0
4. WHEN user_course_progress is created, THE System SHALL enforce CHECK constraint that completion_percentage is between 0.0 and 100.0
5. THE System SHALL create a user_lesson_progress table with columns: id (UUID), user_id (text), lesson_id (FK), completed (boolean), completion_date (nullable), created_at, updated_at
6. THE System SHALL enforce a unique constraint on (user_id, lesson_id) to prevent duplicate lesson progress records
7. WHEN a course is deleted, THE System SHALL cascade delete associated user_course_progress records
8. WHEN a lesson is deleted, THE System SHALL cascade delete associated user_lesson_progress records
9. THE System SHALL create indexes on user_course_progress.user_id and user_lesson_progress.user_id

### Requirement 8: Learning Progress API Endpoints

**User Story:** As an Android developer, I want REST endpoints to fetch user learning progress, so that the app can display in-progress courses, completed courses, and continue learning functionality.

#### Acceptance Criteria

1. WHEN the Android_Client requests GET /api/v1/learning/courses/in-progress, THE System SHALL return all courses where authenticated user has status IN_PROGRESS
2. WHEN the Android_Client requests GET /api/v1/learning/courses/completed, THE System SHALL return all courses where authenticated user has status COMPLETED
3. WHEN the Android_Client requests POST /api/v1/learning/courses/{course_id}/enroll, THE System SHALL create a user_course_progress record with status IN_PROGRESS
4. WHEN the Android_Client attempts to enroll in a course they are already enrolled in, THE System SHALL return HTTP 400 with error message
5. WHEN the Android_Client requests POST /api/v1/learning/lessons/{lesson_id}/complete, THE System SHALL mark the lesson as completed and update related course progress percentage
6. THE System SHALL calculate course completion_percentage based on the ratio of completed lessons to total lessons in that course
7. THE System SHALL return learning data matching the Android LearningCourse domain model schema (id, name, lesson, progress)

### Requirement 9: School Mode Support Schema

**User Story:** As a K-12 student, I want the system to support school subjects, chapters, and exam tracking, so that I can use the app for formal education.

#### Acceptance Criteria

1. THE System SHALL create a subjects table with columns: id (UUID), name, icon, grade_level, board (e.g., CBSE, ICSE), total_chapters (integer), created_at, updated_at
2. THE System SHALL create a user_subject_progress table with columns: id (UUID), user_id (text), subject_id (FK), completed_chapters (integer), progress_percentage (float), created_at, updated_at
3. THE System SHALL enforce a unique constraint on (user_id, subject_id)
4. THE System SHALL create an exams table with columns: id (UUID), user_id (text), title, exam_date, class_name, subject_id (nullable FK), created_at, updated_at
5. WHEN a subject is deleted, THE System SHALL cascade delete associated user_subject_progress records
6. THE System SHALL create indexes on user_subject_progress.user_id and exams.user_id
7. THE System SHALL enforce CHECK constraint that user_subject_progress.progress_percentage is between 0.0 and 100.0

### Requirement 10: School Mode API Endpoints

**User Story:** As an Android developer, I want REST endpoints to fetch subjects and exam data for school mode, so that the app can display school-specific learning content.

#### Acceptance Criteria

1. WHEN the Android_Client requests GET /api/v1/learning/subjects, THE System SHALL return all subjects with user's progress if authenticated
2. WHEN the Android_Client requests GET /api/v1/learning/exams/upcoming, THE System SHALL return all exams for authenticated user with exam_date >= today, ordered by exam_date ascending
3. WHEN the Android_Client requests POST /api/v1/learning/exams with exam data, THE System SHALL create an exam record for authenticated user
4. THE System SHALL return subject data matching the Android Subject domain model schema (id, name, icon, progress, totalTopics, gradeLevel, completedChapters, totalChapters)
5. THE System SHALL return exam data matching the Android UpcomingExam domain model schema (id, title, daysRemaining, className)

### Requirement 11: Database Migrations

**User Story:** As a backend developer, I want all schema changes managed through Alembic migrations, so that schema evolution is versioned, reproducible, and reversible.

#### Acceptance Criteria

1. THE System SHALL use Alembic to generate migration scripts for all schema changes
2. WHEN a migration is auto-generated, THE System SHALL require manual review before applying to verify foreign keys, indexes, constraints, and UUID generation
3. THE System SHALL create separate migration files for each logical schema change (e.g., one for courses, one for roadmaps, one for learning progress)
4. WHEN a migration creates a UUID primary key column, THE System SHALL use server_default=text("gen_random_uuid()")
5. WHEN a migration creates timestamp columns, THE System SHALL use server_default=text("TIMEZONE('utc', NOW())")
6. THE System SHALL test both upgrade and downgrade paths for each migration
7. THE System SHALL document migration dependencies and execution order

### Requirement 12: Seed Data System

**User Story:** As a developer, I want a reproducible seed data system that populates the database with realistic sample data, so that I can test the Android app with meaningful content.

#### Acceptance Criteria

1. THE System SHALL provide a seed script at backend/scripts/seed.py that can be run multiple times idempotently
2. WHEN the seed script is executed, THE System SHALL populate course categories: Programming, Data Science, AI & Machine Learning, Mathematics, Web Development, Computer Science
3. WHEN the seed script is executed, THE System SHALL create at least 3 courses per category with realistic names, descriptions, icons, and accent colors
4. WHEN the seed script is executed, THE System SHALL create at least 3 modules per course with realistic titles and descriptions
5. WHEN the seed script is executed, THE System SHALL create at least 5 lessons per module with realistic titles, content types, and durations
6. WHEN the seed script is executed, THE System SHALL create system roadmaps: Python Developer, Data Science, Machine Learning Engineer, AI Engineer, Full Stack Developer, Frontend Developer
7. WHEN the seed script is executed, THE System SHALL create at least 5 roadmap_items per roadmap with skills, durations, and display order
8. WHEN the seed script is executed, THE System SHALL create subjects for school mode: Mathematics, Physics, Chemistry, Biology, Computer Science, English
9. THE System SHALL use database transactions to ensure seed data is committed atomically
10. THE System SHALL log progress during seeding to indicate which entities are being created

### Requirement 13: API Response Schemas

**User Story:** As an Android developer, I want API responses to match Android domain model schemas exactly, so that the app can deserialize responses without transformation logic.

#### Acceptance Criteria

1. WHEN the System returns course data, THE System SHALL use Pydantic schemas that serialize to match Android Course model (id, name, description, icon, accent)
2. WHEN the System returns roadmap data, THE System SHALL use Pydantic schemas that serialize to match Android RoadmapOption model (id, title, category, description, skills, level, duration, stages, icon, accentTheme)
3. WHEN the System returns learning course data, THE System SHALL use Pydantic schemas that serialize to match Android LearningCourse model (id, name, lesson, progress)
4. WHEN the System returns profile data, THE System SHALL use Pydantic schemas that serialize to match Android UserProfile model (fullName, email, mobile, interests, level, educationMode)
5. THE System SHALL use camelCase naming in API responses to match Kotlin naming conventions
6. THE System SHALL use Pydantic field aliases to convert snake_case database fields to camelCase API responses

### Requirement 14: Error Handling and Validation

**User Story:** As a backend developer, I want comprehensive error handling and validation, so that the API returns meaningful error messages and never exposes sensitive information.

#### Acceptance Criteria

1. WHEN a requested resource does not exist, THE System SHALL return HTTP 404 with message "Resource not found"
2. WHEN request data fails validation, THE System SHALL return HTTP 422 with detailed validation errors
3. WHEN an unexpected error occurs, THE System SHALL return HTTP 500 with message "Internal server error" without exposing stack traces, SQL queries, or credentials
4. WHEN a database constraint violation occurs, THE System SHALL catch the exception and return HTTP 400 with a user-friendly error message
5. THE System SHALL log all errors with sufficient context for debugging without logging sensitive data (passwords, API keys, tokens)
6. WHEN a foreign key constraint fails, THE System SHALL return HTTP 400 with message indicating the referenced resource does not exist

### Requirement 15: Database Query Optimization

**User Story:** As a backend developer, I want optimized database queries with proper session management, so that the API responds quickly and handles concurrent requests reliably.

#### Acceptance Criteria

1. WHEN the System fetches courses with modules and lessons, THE System SHALL use SQLAlchemy joinedload or selectinload to avoid N+1 queries
2. WHEN the System fetches roadmaps with items, THE System SHALL use SQLAlchemy joinedload or selectinload to avoid N+1 queries
3. THE System SHALL use async database sessions from SQLAlchemy 2.x AsyncSession
4. WHEN multiple database operations are logically related, THE System SHALL wrap them in a database transaction
5. THE System SHALL use connection pooling with pool_size=5 and max_overflow=10 for production deployments
6. WHEN paginating results, THE System SHALL use LIMIT and OFFSET with proper ordering to ensure consistent results

### Requirement 16: Authentication Integration

**User Story:** As a backend developer, I want to integrate with user authentication, so that API endpoints can identify the authenticated user and enforce authorization.

#### Acceptance Criteria

1. WHEN an API endpoint requires authentication, THE System SHALL extract user_id from JWT token or session
2. WHEN a user is not authenticated and accesses a protected endpoint, THE System SHALL return HTTP 401 with message "Authentication required"
3. WHEN a user attempts to access another user's data, THE System SHALL return HTTP 403 with message "Access denied"
4. THE System SHALL use user_id as a string identifier to link users to profiles, progress, and personalized roadmaps
5. THE System SHALL support unauthenticated access to GET /api/v1/health, GET /api/v1/courses, and GET /api/v1/roadmaps (system roadmaps only)

### Requirement 17: Database Documentation

**User Story:** As a developer, I want comprehensive database documentation, so that I can understand the schema, relationships, and development workflows.

#### Acceptance Criteria

1. THE System SHALL provide documentation at backend/docs/database.md describing the database schema
2. WHEN the documentation is read, THE System SHALL include an entity-relationship diagram in Mermaid format showing all tables and relationships
3. WHEN the documentation is read, THE System SHALL describe each table's purpose, key columns, and constraints
4. WHEN the documentation is read, THE System SHALL document the migration workflow (creating, reviewing, applying, reverting)
5. WHEN the documentation is read, THE System SHALL document the seed data workflow (running seed.py, idempotency, test data)
6. WHEN the documentation is read, THE System SHALL document environment setup including DATABASE_URL format, required extensions (uuid-ossp), and Supabase configuration

### Requirement 18: API Endpoint Consistency

**User Story:** As an API consumer, I want consistent endpoint patterns, response formats, and error handling, so that the API is predictable and easy to use.

#### Acceptance Criteria

1. THE System SHALL use RESTful URL patterns: /api/v1/{resource} for collections, /api/v1/{resource}/{id} for individual items
2. WHEN the System returns a collection, THE System SHALL use HTTP 200 and return a JSON array
3. WHEN the System returns a single resource, THE System SHALL use HTTP 200 and return a JSON object
4. WHEN the System creates a resource, THE System SHALL use HTTP 201 and return the created resource
5. WHEN the System updates a resource, THE System SHALL use HTTP 200 and return the updated resource
6. THE System SHALL use consistent error response format: {"detail": "error message"}
7. THE System SHALL include CORS headers to allow Android emulator (http://10.0.2.2:8000) and localhost origins

### Requirement 19: Code Organization and Service Layer

**User Story:** As a backend developer, I want a clean separation between routes, services, repositories, and models, so that the codebase is maintainable and testable.

#### Acceptance Criteria

1. THE System SHALL organize route handlers in backend/app/api/routes/{resource}.py files
2. THE System SHALL implement business logic in backend/app/services/{resource}_service.py files
3. THE System SHALL implement database queries in backend/app/repositories/{resource}_repository.py files
4. THE System SHALL define SQLAlchemy models in backend/app/models/{resource}.py files
5. THE System SHALL define Pydantic schemas in backend/app/schemas/{resource}.py files
6. WHEN route handlers receive requests, THE System SHALL delegate business logic to service layer
7. WHEN services need data access, THE System SHALL delegate to repository layer
8. THE System SHALL inject AsyncSession dependencies at the route handler level and pass to services

### Requirement 20: Testing Infrastructure

**User Story:** As a backend developer, I want comprehensive test coverage for API endpoints and database operations, so that I can verify correctness and prevent regressions.

#### Acceptance Criteria

1. THE System SHALL provide pytest-based tests in backend/tests/ directory
2. WHEN tests are executed, THE System SHALL use a separate test database to avoid affecting development data
3. THE System SHALL provide fixtures for creating test data (courses, roadmaps, users, progress)
4. THE System SHALL test successful API responses (HTTP 200, 201) with valid data
5. THE System SHALL test error responses (HTTP 400, 404, 422) with invalid data
6. THE System SHALL test database constraints (unique violations, foreign key violations, check constraints)
7. THE System SHALL test async database operations including transactions and rollbacks
8. THE System SHALL achieve at least 80% code coverage for repository and service layers
